Score-level check (5 queries, top-5 per collection, same embedder):

  all top-5 id lists identical      true
  max absolute score delta          0.000e+00
  top1 scores                      0.751912, 0.579495, 0.585335, 0.689273, 0.719263

Zero delta is the expected result here: the restored vectors are the same
float32 values, and both collections use the same int8 quantization and HNSW
parameters, so scoring follows the same path. It confirms the restore was not
silently de-quantized, re-embedded or re-indexed with different settings.

8. Verdict
----------
PASS. The live collection was snapshotted, restored into a fresh collection on
the same node without hand-creating a schema, came back byte-identical (ids,
payloads, vectors), retained its quantization and HNSW parameters, and produced
exactly the same retrieval results and scores (recall@5 1.0, MRR 1.0, zero
score delta). Both collections survived a Qdrant restart.

9. What this does not prove
---------------------------
- **Same-node, local-file restore.** The snapshot was read with a
  `file:///qdrant/snapshots/...` URI on the node that produced it. Recovery from
  object storage (`s3://`), from an uploaded file into a different cluster, or
  from the Qdrant CLI `--snapshot` start-up path was not exercised.
- **Ten points, 180 KB.** The 0.3 s restore time says nothing about recovery
  time for a multi-gigabyte collection; it is a mechanics check, not a
  recovery-time objective.
- **Single node, one shard, replication factor 1.** No shard rebalancing, no
  replica resynchronization and no partial-failure recovery is covered.
- **No scheduled snapshots.** Capture was on demand through the API. There is no
  cron/policy, retention rule, or restore-into-a-second-environment test.
- **No load test.** Concurrency, sustained throughput and latency under
  pressure remain unmeasured (the p50/p95 in Stage 5 came from sequential
  requests).
- **Restore while serving was not measured.** The API stayed up and bound to
  `rag_documents` throughout; recovery into a second collection name was the
  isolation mechanism, and no assertion is made about API latency during a
  restore of the live collection itself.
