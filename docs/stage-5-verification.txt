  cloud-init status --wait -> done

Defect 1 — block device discovery
---------------------------------
The 200 GB volume attached as /dev/sdb, but cloud-init looked only for
/dev/oracleoci/oraclevdb and /dev/nvme1n1; the oracleoci udev alias is absent on
this image, so vector-lake-mount failed and /mnt/vector-lake did not exist.

Fix in terraform/cloud-init.yaml.tftpl: after the known device paths, fall back
to every whole disk that is not the root disk and does not carry vfat/iso9660.
Re-ran the unit on the host:

  unit: active
  /dev/sdb  196G  40K  186G  1%  /mnt/vector-lake
  LABEL=vectorlake /mnt/vector-lake ext4 defaults,nofail,noatime 0 2

Defect 2 — Qdrant could not write to the volume
-----------------------------------------------
The first container start failed with:

  Failed to write file: Permission denied (os error 13) at path "/qdrant/storage/.atomicwrite..."

Qdrant runs as root but the compose service drops all capabilities
(cap_drop: ALL), which removes CAP_DAC_OVERRIDE; the mounted directory was owned
by uid 1000, so root could not create files in it. Verified by running the same
image with and without the capability drop against the same directory.

Fix: keep the mount point operator-owned (uid 1000) and hand the Qdrant data
directories to root, 0750. This is now part of cloud-init so a rebuilt host
never hits it, and it was applied to the running host.

5. Persistence
--------------
`docker restart cg-vector-qdrant` then `vlake.schema --inspect`:
  points_count 10, status green, optimizer ok
Data lives in /mnt/vector-lake/storage/qdrant on /dev/sdb (ext4 label
vectorlake, fstab by label, nofail), so it survives container restart, host
reboot and instance replacement. The volume is independent of the instance
lifecycle, but `tofu destroy` would delete it — see the MANUAL_PREREQS data
safety note.

6. Pending infrastructure diff (deliberate)
------------------------------------------
Both host fixes are now in `terraform/cloud-init.yaml.tftpl`, and `user_data` is
a force-new attribute. `tofu plan` therefore reports:

  Plan: 2 to add, 0 to change, 2 to destroy
  (instance replacement + its volume attachment)

The block volume is not in that diff, so its data would survive. The replacement
was NOT applied: doing so would destroy the only working host to test a template
that already has a verified manual equivalent on that host (the mount unit and
directory ownership were applied there directly). Exercise it on the next
rebuild or in a second environment. Until then, do not claim the new cloud-init
has booted.
